# ProjectForge app

The mobile app of ProjectForge for iOS and Android (React Native, Expo). Architecture, login flow and plans:
[dev-docs/mobile-app.md](../dev-docs/mobile-app.md); conventions: [CLAUDE.md](CLAUDE.md).

## Setup (macOS)

- Node 24+ and npm on the `PATH` (`brew install node`).
- iOS: Xcode with an iOS simulator runtime (`xcodebuild -downloadPlatform iOS`), CocoaPods.
- Android: Android Studio, started once (its setup wizard installs the SDK), with an emulator of the Device Manager.

The native projects (`ios/`, `android/`) are generated by `expo prebuild` and not in git; `bin/pfApp.sh run` creates
them on its first run.

## Run

```bash
bin/pfDev.sh run 1                              # a server on :8081 (slot 1, test data), from the repo root
projectforge-app/bin/pfApp.sh run 1             # dev client in an iOS simulator, Metro on :19001, login preset to :8081
projectforge-app/bin/pfApp.sh run 1 --proxy     # the same behind the fake SSO proxy (tools/fake-sso-proxy.mjs)
projectforge-app/bin/pfApp.sh metro 1           # only Metro, for an installed dev client
projectforge-app/bin/pfApp.sh check             # tsc (app + projectforge-shared) → eslint → jest
projectforge-app/bin/pfApp.sh help              # the other helpers: sim, proxy, prebuild, build-ios, xcode, …
```

The dev client is the variant `de.projectforge.mobileapp.dev` ("PF Dev"), next to the store app on a device
(`APP_VARIANT`, see `app.config.ts`). The Android emulator reaches the Mac as `10.0.2.2` (`run --android`).

### Behind an SSO proxy

`tools/fake-sso-proxy.mjs` imitates an SSO proxy in forward auth mode (Authentik's outpost): pages without its cookie
go to a login on another host, the api gets a 401 without json, `/rsPublic/` passes. The server needs
`projectforge.app.proxyCookies=authentik_proxy_*` in its `projectforge.properties`. Options: `--ttl` (proxy session),
`--sso-ttl` (the SSO's own session: a second login without a form), `--interactive`, `--guard-public`.

## Texts

`assets/i18n/generated.<locale>.json` is generated from the server's I18nResources by `bin/pfDev.sh gen`, never edited
by hand; app only texts go into `assets/i18n/app.<locale>.json`. Keys are always written out literally:
`t('businessCard.new')`.

## App icon

`assets/icon.png` (1024 × 1024, opaque) is the flame mark of the ProjectForge logo on the dark plate, full-bleed (the
platforms round the corners), `assets/splash-icon.png` the flames on transparent. On Android the launcher masks the icon
itself: `assets/adaptive-icon.png` holds the flames smaller, inside the safe zone, on the plate colour of
`android.adaptiveIcon.backgroundColor`. All are rendered from the master SVGs by `dev-docs/logo/render-logos.py`, never
edited by hand; Expo scales the platform icons from them.

## Release

EAS (`eas.json`): `development` (dev client, simulator), `development-device`, `preview` (TestFlight), `production`.
The store app is `de.projectforge.mobileapp` (team `E4Q65AC7LP`), the update of the earlier Flutter app: version 1.1.0, build
6 and up. OTA updates (EAS Update) reach only builds with the same native code (`runtimeVersion` policy
`fingerprint`). One-time portal steps (App ID, APNs keys, store listing):
[APPLE-SETUP.md](APPLE-SETUP.md).

The Expo account and project aren't in the repository: `app.config.ts` reads `EXPO_OWNER` and `EAS_PROJECT_ID`
(also the EAS Update url), locally from `.env.local` (gitignored), on the build servers from the environment variables
of the EAS project (`eas env:list`, environments `development`, `preview`, `production`). `bin/pfApp.sh eas …` runs
eas-cli with them, for the store app (`APP_VARIANT=production` unless given).

### TestFlight (iOS)

```bash
npx eas-cli@latest login                                     # once: the organization of the project, role Release Manager
printf 'EXPO_OWNER=…\nEAS_PROJECT_ID=…\n' > .env.local       # once, values from the expo.dev project page
bin/pfApp.sh publish                                         # store build (profile production), tag, upload
git push origin app-<version>+<build>                        # the tag it created
```

`publish [production|preview]` checks for a clean tree and an unused tag, runs `check`, builds in the cloud (~10 min),
tags the built commit `app-<version>+<build>` (e.g. `app-1.1.0+8`; it asks, Enter means yes) and submits the build. The tag marks what a
published app reads (dev-docs/mobile-app.md). By hand: `bin/pfApp.sh eas build --platform ios --profile preview`, then
`bin/pfApp.sh eas submit --platform ios --profile preview --latest`, and tag the commit of the build
(`eas build:list` names it).

- Before every build, raise `ios.buildNumber` (and `android.versionCode`) in `app.config.ts` (`appVersionSource`
  `local`): App Store Connect refuses a build number twice per version.
- The signing (distribution certificate, provisioning profile) and the App Store Connect API key of the submit
  (role `APP_MANAGER`) are kept by EAS; the first build asks for the Apple ID (not the team id) once. A push key for
  EAS isn't needed: the server sends with its own APNs keys.
- The submit uploads to the App Store Connect app `ascAppId` of `eas.json`. App Store Connect → TestFlight: after the
  processing (5–15 min), the build goes to the testers.
- Export compliance is answered in the app (`ITSAppUsesNonExemptEncryption: false`).
