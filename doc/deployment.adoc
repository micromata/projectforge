== How to deploy a new release?

The version is set only by the release script (`gradle.properties`, `version=`). Releases are numbered
`X.Y.Z`; `X.Y.0` opens a new version and needs a news entry.

1. Write the changelog: `changelog/changelog.json` (English) and its German translation
   `changelog/changelog.de.json`. The release `X.Y.Z` goes on top of `releases` with the tag `X.Y.Z-RELEASE`.
2. `bin/pfDev.sh release X.Y.Z`: checks the changelog, sets the version, runs `gen` and the build with all
   tests, commits and tags `X.Y.Z-RELEASE`, then commits the next `X.Y.(Z+1)-SNAPSHOT`. Nothing is pushed.
3. `bin/pfDev.sh publish X.Y.Z`: pushes the branch and the tag, and creates the GitHub release with the notes
   generated from the changelog and the jar attached. It asks before each step.
4. Docker images, each architecture built natively (docker or podman, log in first with `podman login
   docker.io` or `docker login`):
    a. On the arm64 machine (e.g. the Mac): `docker/push-release.sh X.Y.Z arch`. It pushes
       `micromata/projectforge:X.Y.Z-arm64` and shows the commands for the other machine.
    b. On the amd64 machine (e.g. a Linux server): `git fetch --tags`, update the branch, then
       `docker/push-release.sh X.Y.Z arch`. The jar is downloaded from the GitHub release.
    c. On either machine: `docker/push-release.sh X.Y.Z manifest`. It pushes the multi-arch tags `X.Y.Z` and
       `latest`.
    d. Check https://hub.docker.com/r/micromata/projectforge/tags: both architectures, amd64 and arm64.

For testing docker images first, please refer `/docker/README.adoc`.
